# Schema changes managed via Supabase CLI migration files

All schema changes — including the initial table creation, RLS policies, and future `ALTER TABLE` additions such as new indicator columns (see ADR 0004) — are written as SQL migration files managed by the Supabase CLI (`supabase migrations new`, `supabase db push`). Migration files live in `supabase/migrations/` in the frontend repository alongside the Edge Function source. Each migration is a plain SQL file with a timestamp prefix; files are committed to source control and applied in order. Migrations are applied manually by running `supabase db push` from a local machine with the `SUPABASE_DB_PASSWORD` set — not via CI — because the Supabase free tier does not support database branching, making automated production migrations risky without a rollback path. This manual gate is intentional: a schema change that cannot be automatically rolled back should require a deliberate human step. The dashboard SQL editor is used only for read-only inspection; no schema changes are made directly through the dashboard. The `supabase/migrations/` directory is the single source of truth for the schema — anyone with the project credentials can recreate the full schema by running `supabase db push` against a fresh project.
